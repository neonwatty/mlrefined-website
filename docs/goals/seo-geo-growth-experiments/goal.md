# SEO And GEO Growth Experiments

## Objective

Turn the completed SEO audit into a staged growth program that improves crawlable page discovery, reader usefulness, GitHub and resource usage, and eligibility for conventional and generative search. Implement the highest-confidence foundations first, publish a small number of substantive source-backed content experiments, deploy safely, and leave measurable Search Console/PostHog/Bing checkpoints.

## Original Request

"Make a detailed plan for each of these SEO/GEO improvement sections and implement it as a GoalBuddy prep board."

## Intake Summary

- Input shape: `existing_plan`
- Audience: Machine Learning Refined readers, instructors, independent learners, search engines, AI answer systems, and the site owner.
- Authority: `approved`
- Proof type: `metric`
- Completion proof: Priority internal-linking and conversion fixes, substantive content experiments, GitHub cross-distribution, crawler/entity readiness, production deployment, and durable search/usage measurement checkpoints are implemented and verified.
- Goal oracle: Live crawlable internal architecture plus Search Console, PostHog, Bing/AI visibility when available, and production smoke evidence showing discovery and resource-use improvement.
- Likely misfire: Shipping metadata, schema, or many thin pages without improving crawlable internal links, reader usefulness, GitHub/resource conversions, or measurable discovery.
- Blind spots considered: Search Console lag; orphaned resource/chapter routes; solutions-manual overclaim risk; platform-controlled AI citations; and the repository's stronger existing authority.
- Existing plan facts: Preserve the completed technical baseline; repair internal links first; improve branded GitHub/PDF pathways and analytics; publish a small source-backed content set; strengthen GitHub cross-links; keep standard/OAI crawlers eligible; and measure with live search and usage evidence.

## Goal Oracle

The oracle for this goal is:

`A final Judge/PM audit proves that the priority internal-linking and resource-conversion architecture is live, the initial substantive learning-page experiments and GitHub distribution loop are deployed, crawler/entity controls remain accurate, and durable Search Console/PostHog/Bing baselines and follow-up outcomes have been recorded.`

The PM must keep comparing task receipts to this oracle. Planning, discovery, a passing tiny slice, or a clean-looking board is not enough. The goal finishes only when a final Judge/PM audit maps receipts and verification back to the original outcome and records `full_outcome_complete: true`.

## Stop Rule

Stop only when a final audit proves the full original outcome is complete.

Do not stop after planning, discovery, or Judge selection if a safe Worker task can be activated.

Do not stop after a single verified Worker package when the broader owner outcome still has safe local follow-up work. Advance to the next highest-leverage reversible package unless a phase, risk, rejected-verification, ambiguity, or final-completion review is due.

Do not stop because a measurement checkpoint needs crawl latency, a credential, or a platform rollout. Record that exact wait state and continue all safe local work. A time-delayed measurement task may remain as the final explicit follow-up when all implementation work is proven complete.

## Slice Sizing

Safe means bounded, explicit, verified, and reversible. It does not mean tiny.

A good task is the largest safe useful slice. A Worker should complete one end-to-end growth package—implementation, focused tests, rendered proof, and analytics behavior—rather than one helper or route at a time.

After two tiny tasks in a row, PM or Judge must reorient the board toward the next demonstrable milestone.
